## Summary

Phishing-resistant MFA is the baseline for authenticating users of online services[^1][^4]. Enforce phishing-resistant authentication by defining authentication strengths in Microsoft Entra ID and applying Conditional Access policies that require these strengths, prioritizing administrative accounts before broad rollout[^3][^2][^4]. Phishing-resistant options include passkeys (FIDO2), Windows Hello for Business, and certificate-based authentication; configure passkeys, CBA, and MFA strength controls through authentication strength policies (including advanced options) as guidance[^1][^5].

  
  
  
  

## Design Decision

> [!NOTE] Enforce phishing-resistant MFA for online services by codifying an authentication strength policy that permits only phishing-resistant methods (FIDO2/passkeys, Windows Hello for Business, or certificate-based authentication) and applies consistently across tenants. Apply the policy via Conditional Access to secure sign-ins across the organization.

## Prerequisites

* **Licensing:** Microsoft Entra ID P1 license is required to use Conditional Access authentication strengths. [^3]
* **Permissions/Roles:** Sign in to the Microsoft Entra admin center as at least a Security Administrator to create authentication strengths. [^3]
* **Dependencies:** Access to the Microsoft Entra admin center and the ability to configure authentication strengths. Availability of phishing-resistant authentication methods (e.g., Passkeys/FIDO2, Windows Hello for Business, Certificate-based Authentication) and Temporary Access Pass options to define authentication strengths. [^3]

## Implementation Steps

### Phishing-resistant MFA via Authentication Strength

1. Sign in to the Microsoft Entra admin center as an administrator. Open Entra ID > Authentication methods > Authentication strengths. Create a new authentication strength. Not provided in source documentation.

2. Name the authentication strength (e.g., "Phishing-Resistant Admin MFA") and select the phishing-resistant methods to allow. Include options such as Passkeys (FIDO2), Windows Hello for Business, Platform SSO, and Certificate-based authentication. Not provided in source documentation.

3. Save the authentication strength configuration. Not provided in source documentation.

4. (Optional) Configure advanced options for Passkeys (FIDO2) to restrict usage. Select Passkeys (FIDO2) > Advanced options. Add allowed AAGUIDs as needed. Not provided in source documentation.

5. Create Conditional Access policies to enforce the new authentication strength for online services. Implement the following patterns found in the guidance:

   - Policy 1 - Admin Protection: Target all admin roles; Require the Admin-Phishing-Resistant authentication strength; Apply to Azure portal and admin centers. Not provided in source documentation.

   - Policy 2 - Standard Users: Target all users (except admins); Require the Passwordless MFA strength; Apply to all cloud apps. Not provided in source documentation.

   - Policy 3 - Legacy Apps: Target legacy applications unable to support modern authentication; Require the Multifactor authentication strength (MFA strength) and block legacy authentication protocols where possible. Not provided in source documentation.

   - Policy 4 - External Access: Target guest/external users; Require MFA with the phishing-resistant strength where feasible. Not provided in source documentation.

   - Policy 5 - Trusted Location: Require MFA for access from untrusted locations; block access from anonymous proxies. Not provided in source documentation.

   - Policy 6 - Risk-Based Control: Require MFA plus password change for medium/high sign-in risk (IdP-protection integration). Not provided in source documentation.

   - Policy 7 - Managed Device: Require compliant devices for access to specific resources (e.g., SharePoint/Azure Web Apps). Not provided in source documentation.

   - Policy 8 - App-Specific Sessions: Enforce restricted session lifetimes (e.g., 30-minute sessions for sensitive apps) and limit data exfiltration (e.g., PHI protections). Not provided in source documentation.

6. Save and enable the CA policies. Not provided in source documentation.

7. Verify phishing-resistant MFA enrollment and policy coverage. Review sign-in logs and CA insights to confirm enforcement. Not provided in source documentation.

8. Document maintenance and training. Not provided in source documentation.

9. Reference resources for implementation and background (remote scripts or templates may be used as needed):

   - Phishing-resistant MFA guidance and patterns. [^1]
   - Custom authentication strength creation and advanced options. [^6]
