## Summary

On Windows 11, version 22H2 and later, LSA protection runs as a protected process by default on clean, HVCI-capable client SKUs if the policy is not configured.[^1]

If enabling via policy, use ConfigureLsaProtectedProcess with values: 0 Disabled, 1 Enabled with UEFI lock, 2 Enabled without UEFI lock.[^1]

Plug-ins loaded into LSA must be digitally signed with a Microsoft signature (WHQL for drivers) and conform to SDL guidance; this is required for loading as a protected process.[^2]

Verify LSA protection status via Event Viewer using the Credential Guard verification guidance.[^3]

## Design Decision

> [!NOTE] LSA protection will be enabled by default on Windows 11, version 22H2 and later client devices. Eligibility requires clean installations on HVCI-capable SKUs where the local LSASS policy is not configured, ensuring LSA runs as a protected process by default.

## Prerequisites

* **Dependencies:** Windows 11, version 22H2 (10.0.22621) or later; device is a cleanly installed, HVCI-capable client SKU. [^1]

[^1]: [Policy CSP - LocalSecurityAuthority ConfigureLsaProtectedProcess](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-lsa#configurelsaprotectedprocess)

## Implementation Steps

### LSA protection defaults and configuration

1. On Windows 11, version 22H2 and later, LSA protection may run as a protected process by default if the policy is not configured and there is no registry setting. This baseline behavior applies to cleanly installed, Hypervisor-enforced Code Integrity (HVCI) capable client SKUs. The default configuration is not UEFI locked. [^1]

2. To explicitly enable LSA protection, configure the Local Security Authority policy ConfigureLsaProtectedProcess to one of:
   - EnabledWithUEFILock (UEFI-locked)                    — LSA runs as a protected process with UEFI lock.  
   - EnabledWithoutUEFILock (not UEFI-locked)           — LSA runs as a protected process without UEFI lock.  
   - Disabled                                              — LSA does not run as a protected process.  
   This policy is located under Device Configuration at the path shown in the policy documentation. [^1]

3. Use the following policy values:
   - 0 (Default): Disabled. LSA won't run as a protected process.  
   - 1: Enabled with UEFI lock. LSA will run as a protected process and this configuration is UEFI locked.  
   - 2: Enabled without UEFI lock. LSA will run as a protected process and this configuration isn't UEFI locked.  
   These values determine whether LSA protection is active and how it can be managed. [^1]

4. Criteria to allow LSA protection to run as a protected process
   - LSA plug-ins or drivers loaded into LSASS must be digitally signed with a Microsoft signature. Drivers that are WHQL-certified are supported; unsigned or non-Microsoft-signed plug-ins fail to load in LSA. SDL-compliant development is also required. [^2]
   - All correctly signed plug-ins must load into LSA and function as expected. Use audit logs to identify plug-ins or drivers that fail to run as a protected process. [^2]
   - If added LSA protection is enabled, debugging LSASS or LSA plug-ins is not supported. Planning and testing should account for this limitation. [^2]

5. Recommended testing before broad deployment
   - Identify all LSA plug-ins and drivers (including non-Microsoft and internally developed components). [^2]
   - Ensure every LSA plug-in is digitally signed with a Microsoft certificate. [^2]
   - Validate that all correctly signed plug-ins load into LSA and operate as intended. [^2]
   - Review audit logs to identify any plug-ins or drivers that fail to run as a protected process. [^2]

6. Verification of default behavior and enabled state
   - If the policy is not configured, LSA protection may run by default on eligible devices. Verify the current state using supported verification methods described below. [^1]

7. Verification methods (including Event Viewer)
   - System Information: Open msinfo32.exe, go to System Summary, and confirm Credential Guard is listed as enabled next to Virtualization-based Security Services Running. [^5]
   - PowerShell: In an elevated PowerShell session, run:
     ```powershell
     (Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard).SecurityServicesRunning
     ```
     A value of 1 indicates Credential Guard (LSA protection) is enabled; 0 indicates it is disabled. [^5]
     ```powershell
     (Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard).SecurityServicesRunning
     ```
   - Event Viewer: Use Event Viewer to verify Credential Guard status as described in official deployment guidance. See the referenced Windows Enterprise features documentation for steps. [^5]

8. References for implementation and verification
   - ConfigureLsaProtectedProcess policy details, including default behavior and value mappings. [^1]
   - Protected process requirements for plug-ins or drivers (digital signing, WHQL, SDL, testing). [^2]
   - Credential Guard verification guidance and event-based verification options. [^5]
