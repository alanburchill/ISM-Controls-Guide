# Multi-factor authentication used for authenticating users of online services is phishing-resistant.

## Summary

Configure **USR - G - Require strong auth** via Microsoft Entra ID Conditional Access to require multifactor authentication with phishing-resistant strength, targeted to the required user set.[^1]

Phishing-resistant MFA methods may not always be possible; strictly phishing-resistant options include **FIDO2 security keys** and **Windows Hello for Business**, while the Microsoft Authenticator app provides phishing resistance but is not strictly phishing-resistant.[^2]

[^1]: [ISM controls and multifactor authentication maturity levels - Essential Eight - Microsoft Learn](https://learn.microsoft.com/en-us/compliance/anz/e8-mfa-ism)
[^2]: [ASD Blueprint: Authentication - ASD's Blueprint for Secure Cloud](https://blueprint.asd.gov.au/design/platform/identity/authentication/)

## Design Decision

Use **Microsoft Entra ID** to (1) configure **USR - G - Require strong auth** and (2) deploy **ScriptName.ps1** via **Microsoft Entra Conditional Access**.

> [!NOTE]
> Deploying the policy enforces phishing-resistant MFA; best judgement should be used when selecting authentication strength.

## Prerequisites

### Permissions/Roles

- **Conditional Access Administrator**: Required to sign in to the Microsoft Entra ID admin center and create conditional access policies that require phishing-resistant MFA.[^1]

- **Authentication Policy Administrator**: Required to create and manage authentication strengths and passkey policies.[^2]

- **Authentication Administrator**: Required for provisioning FIDO2 security keys and related authentication method configurations.[^3]

## Implementation Steps

### Configure Policy using Settings Catalog

1. Create a new conditional access policy named **USR - G - Require strong auth**. Target the user group as required.[^1]

2. Under the policy, configure:
   - Users: Include the required users or groups.
   - Cloud apps: Include All cloud apps.[^1]
   - Grant: Require authentication strength, then select phishing-resistant MFA strength. This enforces phishing-resistant authentication for sign-in.[^2]

3. Save and enable the policy. Verify that sign-ins trigger the configured authentication strength.[^1]

4. Review the available phishing-resistant options. Only **FIDO2 security keys** or **Windows Hello for Business** are considered strictly phishing-resistant; the **Microsoft Authenticator app** is not strictly phishing-resistant but is resistant to phishing and is better than many other methods.[^4]

> [!NOTE]
> Phishing-resistant MFA methods may not always be possible. Use best judgement when selecting authentication strength. Only FIDO2 security keys or Windows Hello for Business are strictly phishing-resistant; the Microsoft Authenticator app is not strictly phishing-resistant but is resistant to phishing and is much better than other forms of authentication. [^4]

### Define Authentication Strengths and Apply to Policy

1. In Microsoft Entra ID, navigate to **Authentication methods** > **Authentication strengths**. Create a new strength (e.g., **USR - G - Phishing-Resistant Strength**).[^5]

2. Add allowed methods for the strength:
   - Passkeys (FIDO2) (device-bound)  
   - Windows Hello for Business  
   - Optionally, omit weaker methods where applicable. This aligns with guidance to phishing-resistant options. [^7]

3. In the conditional access policy from the first section, set:
   - Grant: Require authentication strength
   - Choose the strength created in step 1 (e.g., **USR - G - Phishing-Resistant Strength**).[^3]

4. Save the authentication strength policy and the conditional access policy. Test sign-ins for a representative user.[^3]

5. Note: Phishing-resistant MFA strength adoption should consider device capabilities and user role. Follow guidance on recommended authenticator types for your environment. See ASD blueprint for context on FIDO2 and Windows Hello for Business integration.[^4]
