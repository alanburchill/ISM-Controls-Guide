## Summary

Configure a conditional access policy that requires multifactor authentication with phishing-resistant strength.[^1][^2] Policy naming and targeting should align with ASD blueprint guidance (e.g., "USR - G - Require strong auth").[^5]

Not provided in source documentation.

Phishing-resistant MFA methods include Windows Hello for Business, Passkeys (FIDO2), and Certificate-Based Authentication; Microsoft Authenticator is not phishing-resistant but provides phishing resistance and is better than other forms.[^6][^3]

## Design Decision

> [!NOTE] A Conditional Access policy named 'USR - G - Require strong auth' will be deployed to enforce phishing-resistant MFA for required users, prioritizing FIDO2 security keys and Windows Hello for Business; where phishing-resistant methods are not feasible, best judgement will apply, and Microsoft Authenticator is allowed but not strictly phishing-resistant.

## Prerequisites

* **Licensing:** Microsoft Entra ID P1 or P2 licensing may be required; these SKUs are included with Microsoft 365 E3/E5. Enable security defaults where applicable. [^1]
* **Permissions/Roles:** Configure Conditional Access with User/Group Assignment set to All users, excluding break glass accounts. [^2]
* **Dependencies:** Microsoft Intune is required to enable Windows Hello for Business as part of device enrollment. [^3]

## Implementation Steps

### USR - G - Require strong auth

1. Configure phishing-resistant authentication strengths in Entra ID.
   - In the Microsoft Entra admin center, navigate to Protection > Authentication methods > Authentication strengths and create a new authentication strength. Configure strengths for the required maturity level using the guidance table. [^1]

2. Create a Conditional Access policy named "USR - G - Require strong auth" to enforce phishing-resistant MFA.
   - Create a new Conditional Access policy. Set User/Group assignments to include the required users (for example, All users, excluding break glass accounts) and App assignments to All resources. Under Grant controls, select “Require Authentication Strength” and choose the phishing-resistant MFA strength. Begin with a test deployment in a non-production or report-only mode to collect sign-in data before enforcement. [^2]

3. Plan enforcement and rollout.
   - After testing, use the readiness workbook to identify users/devices ready for enforcement. Create groups accordingly and move the policy from report-only to enforcement for those groups. [^2]

4. Phishing-resistant methods guidance.
   - Phishing-resistant MFA methods may not always be possible; use best judgement when selecting authentication strength. Only FIDO2 security keys or Windows Hello for Business are strictly phishing-resistant; the Microsoft Authenticator app is not technically phishing-resistant but is resistant to phishing and is better than other forms of authentication. [^3][^4][^5]

5. Policy naming and targeting guidance.
   - Align the policy with ASD blueprint conventions and target appropriate user groups as required. [^3]
